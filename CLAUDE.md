# CLAUDE.md — standing rules for ai-agent-mcp-eval-suite

These rules apply to every agent and every change in this repository.

## Workflow

- Plan first after the bootstrap. Write the plan as a document under `docs/plans/`, open a draft PR that contains only the plan, and stop for the reviewer's approval before building.
- Work on `feat/YYYY-MM-DD-<slug>` branches only. Never use `claude/` branch names.
- Only the bootstrap commit goes directly to `main`. After that, every change goes through a `feat/` branch and a draft PR.
- Never squash, rebase, amend or force-push. Merge commits only.
- The builder never merges and never tags. The owner merges and tags.
- Never enable auto-merge unless the owner asks.

## Commits and pull requests

- Use Conventional Commits with lowercase subjects, for example `feat: add stub fixture loader`.
- No commit trailers. Do not add `Co-Authored-By`, `Signed-off-by`, or "Generated by" lines to commits.
- No "Generated by" footers in pull request bodies.
- Never write the owner's personal name in code, docs, commits or PRs. Say "the owner" or "the reviewer". Repository URLs and local folder paths are fine. The only exceptions are the copyright line in `LICENSE` and the one contact line in `README.md`.

## Upstream repositories

- Never edit product forks: `https://github.com/Jayami123/openclaw` and `https://github.com/Jayami123/LibreChat` are reference only.
- LiteLLM is not forked. Use it as published, pinned by version or digest.
- Do not run CodeRabbit.
- Do not use the Bridge-bss account.

## Engineering

- Industry-standard practice first. If a choice is non-standard, flag it in the plan or PR and name the standard alternative.
- Pin container images by digest.
- Pin GitHub Actions by full commit SHA, with the version in a trailing comment.
- Bind every local port to `127.0.0.1`.
- Harness dependency: `qa-portfolio-harness` is consumed as an npm git dependency pinned to a tag or SHA. Never pin `main`.
- The harness owns product start and stop. Tests do not start or stop products themselves.
- TypeScript, Node >= 20, NodeNext modules, `strict` on. `npm run check` must pass before a PR is marked ready.
- Tests run with `tsc` then `node --test`.

## Secrets and data

- Never commit secrets. `.env` and `.harness/` are git-ignored.
- Generate passwords and keys per run into `.harness/`. Never reuse them across runs.
- Never print secrets or tokens, in logs, reports, PR text or chat.
- `GEMINI_API_KEY` is only an Actions secret in a GitHub Environment. Never put it in the repo, in `.env.example`, in a PR, in chat, or in a cloud builder.
- No `GEMINI_API_KEY` in cloud sessions. Cloud sessions run in stub mode.
- Fake data only. Never use real customer or personal data in fixtures.

## Mode and reporting

- `P4_LLM_MODE` defaults to `stub`. Nightly runs set it to `nightly`.
- Report real command output only. Never report a check as passing unless it was run and its output was read.
- If a test or check fails, say so with its output.

## Case IDs

- Do not invent case IDs. Case IDs come from the case ledger (`p4-case-ledger.csv`) only.
- Do not implement or close L3, L4 or L5 cases in L1 work.
