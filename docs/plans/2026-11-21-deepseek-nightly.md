# Plan: nightly model jobs on DeepSeek (harness v0.6.11)

Date: 2026-11-21. Branch: `chore/2026-11-21-deepseek-nightly`. Status: draft plan. No code is changed by this PR.

## Goal

Run both nightly model jobs on DeepSeek instead of Gemma, through `qa-portfolio-harness` v0.6.11:

- `P4_NIGHTLY_PROVIDER=deepseek`, so `p4-nightly` routes to `deepseek/deepseek-flash`.
- `DEEPSEEK_API_KEY` from the `nightly-gemma` GitHub Environment. `GEMINI_API_KEY` is removed from the nightly jobs.
- The outage rule recognises the DeepSeek and LiteLLM upstream error forms. The rule itself does not change: evidence must be in the trial's own LiteLLM time window.

No new case IDs. No L3, L4 or L5 case is implemented or closed here.

## Decisions

1. **Harness pin.** `package.json` moves `qa-portfolio-harness` from `#v0.6.10` to `#v0.6.11`, and so does the `allowScripts` key. `package-lock.json` is regenerated by `npm install`, never edited by hand. The local `node_modules` has an older harness (0.6.1) than the v0.6.10 pin, so the lock change is taken from a clean `npm install`.
2. **Workflow.** In `nightly.yml`, the two model jobs (`gemma` smoke and `gemma-measured-mattermost`) get:
   - `P4_NIGHTLY_PROVIDER: deepseek`
   - `DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}`
   - `GEMINI_API_KEY` removed
   - the fail-closed step checks `DEEPSEEK_API_KEY` and never prints it
   - the environment stays `nightly-gemma`, as requested
   - the `l4-openclaw-full` job is stub only and is not changed
3. **Job ids.** The ids `gemma` and `gemma-measured-mattermost` are kept, because `needs: gemma` and the `concurrency` group use them and no branch protection rule names them. Only the display names change, to `model l1 smoke` and `model measured l3 mattermost (INJ-013)`. The `nightly-gemma` concurrency group and environment name stay, because the owner asked for them to stay.
4. **Outage patterns.** `tests/l1/provider-outage.ts` gets three outage forms, matched by the LiteLLM class prefix:
   - `litellm.ServiceUnavailableError` (503)
   - `litellm.BadGatewayError` (502)
   - `litellm.InternalServerError` (500)

   The existing `UNAVAILABLE` (Vertex) and the other words stay.
5. **429 is not an outage (decision for the reviewer).** The request listed `RateLimitError` (429) among the outage forms. The reviewed rule says a rate limit is `partial` only after the retries are used up, and that it is never `inconclusive`. This plan keeps that rule: a `litellm.RateLimitError` stays `partial` and is not added to the outage words. If the reviewer wants 429 to count as an outage, that changes a reviewed rule and needs a sign-off.
6. **500 and 502 as outages.** Both are upstream failures in which the model did not answer, so they follow the existing outage rule (inconclusive, never a pass). A reviewer may prefer 500 to count as a real error. That is a one-line change.
7. **Same window rule.** The new patterns are read only through the existing functions (`isProviderOutage`, `outageLogLine`, `windowLines`, `classifyEmptyAnswer`, `classifyStall`). An outage line outside the trial's own time window is not counted.
8. **Docs.** `docs/ci.md`, `README.md` and `docs/cloud-environments.md` describe DeepSeek as the nightly model. Gemma wording stays only where it is history (for example the Gemma lane results recorded with run ids). Plan files under `docs/plans/` are history and are not edited.

## Changes the list did not name (found while reading, needed for a green and honest run)

- **`tests/l1/gemma-tool-call.e2e.ts` gates on `GEMINI_API_KEY` (line 17).** If the workflow passes only `DEEPSEEK_API_KEY`, the L1 smoke test would skip and the lane would still be green with nothing measured. The gate becomes `DEEPSEEK_API_KEY` in the same change. The same check is made in `tests/l1/librechat-stub-tool-call.e2e.ts` and `tests/l1/openclaw-stub-tool-call.e2e.ts` only to delete the key in stub mode, and those lines stay.
- **Other `GEMINI_API_KEY` references** in `tests/l3/support/case.ts`, `tests/l3/support/stack.ts`, `tests/l4/support/case.ts` and `scripts/l4-stack.mjs` are read during the build. Any that gate or pass a nightly key switch to DeepSeek. Stub-mode guards that only delete the key stay. The comment-only references in `.github/workflows/pr.yml` are not changed (the PR gate is stub only).
- **Trial records.** The served model id in a measured record comes from LiteLLM `/model/info`, so it becomes `deepseek/deepseek-flash`. `src/stats/config.ts` lists only `gemma-4-31b-it` as an approved model. The model-swap gate treats any other model as not approved. This plan does not change that list, because adding a model is an owner decision. The DeepSeek trial records will show `deepseek/deepseek-flash` as the served id.
- **Unit tests.** Every new outage pattern gets a test, in the same style as `tests/l1/gemma-classify.test.ts` and `tests/l1/stall-classify.test.ts`. The tests cover each prefix inside the window (outage), the same prefix outside the window (not counted, red), a 429 that stays partial, and a real answer with no tool call (a normal fail). The fixture lines are built from the LiteLLM prefixes above, not from invented DeepSeek wording.

## Risks

- DeepSeek publishes no RPM or TPM, so the pacing rests on the per-trial spacing alone. The lanes still run one after another.
- If DeepSeek's real error body does not contain the LiteLLM prefix in the trial log, the outage would be classified as a red infrastructure failure rather than inconclusive. That is the safe direction (never a pass), but it would be noisy. The first dispatched run would show it.
- The `nightly-gemma` Environment may restrict deployment branches, which would block the dispatch from this branch.
