Deviations from the master plan, flagged per CLAUDE.md ("name the standard alternative"). **Deviations 1 to 3 were approved by the reviewer; deviation 4 is recorded by the reviewer's decision and is repeated in `README.md`.**

1. **Test folder is `tests/l4/`, not `tests/openclaw/appr/ ...`.** The request for this plan says `tests/l4/`; L1 uses `tests/l1/`. Mapping: `tests/openclaw/appr/` becomes `tests/l4/appr/`, and so on. Standard alternative: the master plan's path.
2. **Fixtures go in `src/stub/fixtures/oc-*.json`, not `tests/fixtures/openclaw/`.** `.dockerignore` excludes `tests`, and the stub image copies only `src/stub/fixtures`. Using the existing folder needs zero shared-file edits. Standard alternative: `tests/fixtures/openclaw/`, which costs three shared edits (`.dockerignore`, `docker/stub/Dockerfile`, a multi-directory `STUB_FIXTURES_DIR` in `src/stub/main.ts`).
3. **The stack is started once by a script, not by each test.** 62 test files cannot each cold start OpenClaw (about 30 s ready time per the harness). L1 tests call `adapter.up()` themselves because there are only three. L4 uses `scripts/l4-stack.mjs up|down` (shared file, section 8) that calls the same harness adapters; tests only check the stack is there and fail closed, as `requireStubContainer()` does. Standard alternative: each test file starts and stops the stack.
4. **Telegram is the WhatsApp-style mock transport.** The master plan says "WhatsApp-style" traffic goes through a mock channel with no real WhatsApp numbers. L4 models it as a Telegram Bot API-shaped server, because OpenClaw's own `qa-channel` is not in the release image (F1) and the bundled Telegram channel accepts a custom `apiRoot` and has the DM, group, reaction, reply, quote and attachment surfaces the cases need (F2). No real number, no ban risk. Standard alternative: a WhatsApp transport mock; rejected because WhatsApp needs the Baileys session protocol, not a REST shape. Approved by the reviewer.

## 3. Findings that shape the design

| # | Finding | Evidence | Consequence |
|---|---|---|---|
| F1 | OpenClaw's own `qa-channel` is **not shipped** in the release package or image. | `package.json` `files` excludes `dist/extensions/qa-channel/**`; `docs/plugins/reference/qa-channel.md` says "Install route: source checkout only". | We cannot reuse it. Master plan says build our own mock channel. |
| F2 | Telegram **is** bundled (`dist/extensions/telegram`) and accepts `apiRoot` (custom Bot API root), `dmPolicy: pairing`, `allowFrom`, `groupPolicy`, `groupAllowFrom`, `groups`, `reactionNotifications`, `actions.*`. Bot API is plain HTTPS+JSON with long polling. | `docs/channels/telegram.md`. | The mock channel is a **Telegram Bot API-shaped server**. It has DM, group, reaction, reply, quote, attachment: everything the "WhatsApp-style" cases need, with no real number and no ban risk. Standard alternative: a WhatsApp transport mock. Rejected: WhatsApp needs the Baileys session protocol, not a REST shape. |
| F3 | Harness 0.6.3 writes `channels: {}` and a fixed config. No channel, no memory or skill seeding, no per-run config knobs. | `openClawConfig()` in `openclaw-env.ts`. | Channel cases need a harness change (H1). Listed in section 8, not made here. |
| F4 | `runTask()` returns **client** function tools without executing them. Approvals only fire on OpenClaw's **built-in** tools (`exec`, `message`, `memory_*`, file tools). | L1 finding; `docs/tools/exec-approvals.md`. | L4 stub fixtures call built-in tools. The oracle is the stub recorder's `toolResults` (what OpenClaw sent back: result or denial) plus product state. `runTask` is only the driver. |
| F5 | `/v1/responses` with shared-secret auth runs **owner-sender turns**. Non-owner behaviour (unpaired, allowlist, group, spoof) only exists through a channel. | `docs/gateway/openresponses-http-api.md`. | Every non-owner case is a channel case. |
| F6 | `web_fetch` blocks private and internal hosts. Our fixture pages live on the private `qa-harness-p4` network. | `docs/tools/web-fetch.md` (`dangerouslyAllowPrivateNetwork: false`). | Cases that need the agent to open a planted page (`P4-OC-INJ-003`, `P4-OC-MEM-005`) need a config knob (H4). `P4-OC-ADV-003` (SSRF) gets the opposite and passes on the default. |
| F7 | The stub picks a fixture by the `[fixture:id]` marker; two **different** ids in one conversation give HTTP 400. The same id repeated is fine (it is a set). Turn index = number of `role: "tool"` messages. | `src/stub/server.ts`. | Every multi-message case uses **one fixture id in every message** and scripts all turns in that one fixture. Planted text must never contain a different marker. |
| F8 | The stub cannot return an HTTP error turn. | `fixtures.ts` has `tool_calls` or `content` only. | Step 0 adds error turns to the stub as the first commits of the build PR (decided by the reviewer), so `P4-OC-REL-004` is a Tier A case. |
| F9 | Pending approvals, the allowlist and memory are files and SQLite rows in the state volume `qa-harness-openclaw-state`: `state/openclaw.sqlite#exec_approvals_config`, `MEMORY.md`, `memory/*.md`, `skills/`. | docs. | Oracles read them read-only through `docker exec` on the harness-owned container. Reading is not start or stop. Seeding uses the same path until the harness has a seed primitive (H2). |

Design principle that follows from F4 and the master plan section 6: **in stub mode the "model" is a scripted compromised model.** The fixture performs the attack call; the stub test proves the *gate* (approval, allowlist, pairing, scope) blocks it and leaves state unchanged. Whether a real model falls for the injection is measured nightly with Gemma at k trials, which is L5's number. So measured cases (`P4-OC-INJ-005..008`) run plumbing only in stub mode, as the master plan says.

### Step 0: stub error turns (the first commits of the build PR)

Reviewer decision: this lands first, inside the build PR, so `P4-OC-REL-004` is not deferred. It is the only edit this lane makes to `src/stub/`; L1's own tests are not edited.

1. `src/stub/fixtures.ts`: a turn is now exactly one of `tool_calls`, `content`, `error` or `close`.

```ts
export interface TurnSpec {
  tool_calls?: ToolCallSpec[];
  content?: string;
  /** HTTP error answer, OpenAI-shaped body. Status 400 to 599. */
  error?: { status: number; message: string };
  /** Destroy the connection without a response (a closed stream). */
  close?: true;
}
// validateFixture: count the present keys among tool_calls, content, error, close; anything other than exactly one fails with
// "each turn needs exactly one of tool_calls, content, error or close". An error status outside 400..599 fails.
```

2. `src/stub/server.ts`: before building `callList`, handle the two new turn kinds. The turn index is unchanged (it counts `role: "tool"` messages), so a retry of the same request gets the same error again, which keeps the stub deterministic.

```ts
if (turn.close === true) {
  trace.push({ seq: trace.length + 1, fixture: id, turn: turnIndex, toolsOffered: toolNames(body.tools), stream: body.stream === true,
    toolResults: [], toolCalls: [], content: null, error: "closed" });
  req.socket.destroy();
  return;
}
if (turn.error !== undefined) {
  trace.push({ /* same fields */ error: turn.error.status });
  sendJson(res, turn.error.status, { error: { message: turn.error.message, type: "p4_stub_error" } });
  return;
}
```

### 6.5 Modes, CI and the nightly budget

- **PR gates use the stub only.** `P4_LLM_MODE=stub`; `GEMINI_API_KEY` is deleted from the environment in `l4Case`. The L4 PR job has no secrets and is safe for fork PRs.
- **Nightly: one lane at a time.** The existing workflow already serialises on `concurrency: group: nightly-gemma, cancel-in-progress: false`. The L4 nightly job joins that group, so it queues behind L1 and L3 and never runs in parallel. TPM 16K is shared across all lanes.
- **Which L4 cases run on Gemma (measured):** `INJ-001, INJ-005, INJ-006, INJ-007, MSG-011, MSG-012, MEM-005, APPR-006`. Everything else is a hard gate and runs only on the stub.
- **Budget arithmetic** (planning estimate only, from the master plan's "about 6,000 tokens per heavy turn, 2 to 3 turns per minute"): 8 IDs x k=10 x 2 turns = 160 turns, about 960K tokens, at 16K TPM at least 60 minutes. The L4 slice therefore runs on its own nights and resumes with the L5 cursor (`--slice openclaw --resume evidence/nightly/cursor.json`). A 429 gives `partial`, a safety refusal gives `blocked by provider`; neither is a pass or a fail.
- **Nightly needs H5:** OpenClaw's primary model is fixed to `p4-litellm/p4-stub`; Gemma needs `p4-nightly`. L1's Gemma test only ran through LibreChat, so OpenClaw on Gemma is untested.
- The measured assertion in stub mode is skipped inside the test body, with the plumbing (fixture delivered, oracle hooked, trace schema valid) still running.
